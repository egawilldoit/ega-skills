## C1 — Live OAuth discovery (G41, G42)

Commands (production, read-only; curl):

```
curl -sS -w '%{http_code}\n' https://ega-skills-mcp.vercel.app/healthz
curl -sS -w '%{http_code}\n' https://ega-skills-mcp.vercel.app/readyz
curl -sS -w '%{http_code}\n' https://ega-skills-mcp.vercel.app/.well-known/oauth-protected-resource
curl -sS -w '%{http_code}\n' https://ega-skills-mcp.vercel.app/.well-known/oauth-protected-resource/mcp
curl -sS -D - -o /dev/null -X POST https://ega-skills-mcp.vercel.app/mcp \
  -H 'content-type: application/json' -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}'
```

Observed (G41):

- `/healthz` → `200 {"status":"ok"}`; `/readyz` → `200 {"status":"ready"}`.
- Both discovery paths → `200` with the same canonical document:
  `resource=https://ega-skills-mcp.vercel.app/mcp`,
  `authorization_servers=["https://divriwexbijtojjulqtu.supabase.co/auth/v1"]`,
  `bearer_methods_supported=["header"]`. No secret material, no debug fields.
- `POST /.well-known/oauth-protected-resource` → `405`; unknown route →
  `404 {"error":{"code":"E_NOT_FOUND"}}`.

Observed (G42, header spoof):

- `Host: evil.example` + `X-Forwarded-Host: attacker.example` →
  Vercel edge answers `404 DEPLOYMENT_NOT_FOUND` before the application, so a
  spoofed Host can never reach the runtime (platform-level identity binding).
- `X-Forwarded-Host`/`Forwarded` alone (Host unchanged) → metadata still
  returns the canonical production resource, and the 401 challenge still points
  at `https://ega-skills-mcp.vercel.app/.well-known/oauth-protected-resource`.
  The canonical resource is configured once at startup and never header-derived
  (`packages/mcp/src/hosted-oauth.ts`).

## Tradeoffs and structural findings

1. **No distinct staging audience.** `supabase/migrations/20260919090000_oauth_mcp_audience_hook.sql`
   hard-binds every delegated token's `aud` to
   `https://ega-skills-mcp.vercel.app/mcp`; changing it is a production DB
   change that is not authorized. The least-bad staging profile was therefore
   used: the preview deployment is configured with the *same* dedicated
   resource/audience and issuer, and staging is isolated by deployment identity
   (immutable preview URLs, separate IDs, per-deployment env) rather than by
   audience. Preview smoke and delegated-token MCP calls prove the candidate
   release behaves identically to production.
2. **Real clients must use the production origin.** Both Codex and OpenCode
   enforce that the protected-resource metadata `resource` equals the MCP URL
   they connect to. Pointing Codex at a preview URL fails with
   `Metadata error: Protected resource metadata resource mismatch: reference

   Consequently C8/C9/C10/C11 real-client acceptance runs against
   `https://ega-skills-mcp.vercel.app/mcp`, which serves exactly the candidate

3. **Preview SSO protection.** Preview deployments require the project's
   automation bypass header; harnesses inject it via

   resource-metadata mismatch in (2) blocks them regardless.
4. **SQLite byte non-determinism.** Candidates A and B are different artifact
   byte streams with identical release identity; the runtime verifies the
   digest recorded in `release-package.json`, so both are self-consistent.

## Fix round (post-review)

Reviewers R1/R2 reviewed integration SHA `1e5e87b` and returned BLOCK with
three findings routed to this agent. All three are fixed on this branch and
verified below. The CI failure that motivated FIX 1 is run `35782175610`
(job `106930103001`), which failed at
`tests/oauth/jwt-containment.test.mjs:141` with
`AssertionError: tampered signature must be rejected with 401 / 200 !== 401`.

### FIX 1 (P1) — deterministic tampered-signature negative

Root cause: the tamper helper flipped the LAST base64url character of the
64-byte ES256 signature (`tamper(parts[2], parts[2].length - 1)`). The final
base64url character of a 64-byte payload carries only 2 data bits, so a
text-level flip can decode to the identical byte; the token stayed valid and
the 401 assertion failed intermittently (reviewers measured ~24% no-op, 3/8
local failures).

Fix (`tests/oauth/jwt-containment.test.mjs`): decode the signature with
`Buffer.from(parts[2], "base64url")`, flip bit 0 of a real data byte
(`tampered[0] ^= 0x01`), re-encode, and assert both the decoded bytes and the
encoding differ from the original before the negative loop runs. Every other
negative and every 401/Bearer/no-catalog assertion is unchanged.

Determinism proof (command and observed result):

```
for i in $(seq 1 20); do node --test tests/oauth/jwt-containment.test.mjs; done
→ 20/20 consecutive green runs, 0 failures (each run: 2 tests, 2 pass, 0 fail)
```

### FIX 2 (P2) — preserve frozen tool error codes

Root cause: `errorResult` in `packages/mcp/src/hosted.ts` mapped every
non-`HostedRuntimeError` to `E_RUNTIME_UNAVAILABLE`, collapsing frozen
`McpContextError` codes such as `E_CONTENT_FILE_UNKNOWN` and
`E_VERSION_NOT_FOUND`.

Fix: import `McpContextError` from `./project-context.js` and preserve its
`.code`; `HostedRuntimeError` keeps its mapping and unknown errors still answer
`E_RUNTIME_UNAVAILABLE`. Message text is unchanged.

Regression test (new, self-contained, `tests/mcp/hosted-content-codes.test.mjs`):
hosted `get_content` with `file_path` `"hub-release.json"`,
`"../hub-release.json"`, and `"references/unknown.md"` each return
`isError: true` with code `E_CONTENT_FILE_UNKNOWN`; a valid `get_content`
still returns content. Codes are asserted, not messages.

### FIX 3 (P2) — authorization precedes deny classification

Root cause: `guard` checked `deniedSkills`/`deniedSources` before
`authorizeResource`, so an authenticated-but-unauthorized principal could
distinguish a denied skill (`E_CONTENT_REVOKED`) from a nonexistent one
(`E_UNAUTHORIZED`).

Fix: `authorizeResource(tool, skillId)` now runs before both deny checks; the
post-body fresh-authorization check is unchanged. Unauthorized principals
receive `E_UNAUTHORIZED` for denied and nonexistent skills alike; authorized
principals still receive `E_CONTENT_REVOKED` for denied skills.

Regression tests (same new file): an unauthorized principal gets the identical
`E_UNAUTHORIZED` code for a denied skill and for a nonexistent skill; an
authorized principal still gets `E_CONTENT_REVOKED` for the denied skill and
content for an allowed skill. `tests/mcp/hosted-deny-policy.test.mjs` remains
green (it asserts `isError`, not the specific code, for this case).
